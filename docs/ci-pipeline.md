# CI pipeline

Every workflow defaults to `permissions: contents: read`, pins actions by commit SHA, and holds no secrets. Deploys never run from Actions.

| Workflow | Trigger | What it gates |
|---|---|---|
| `actionlint.yml` | PRs touching `.github/**` or shell scripts | actionlint + shellcheck |
| `contracts.yml` → `_contracts.yml` | PRs touching `contracts/**`, toolchain pins, the lockfile or these workflows | `evm`: forge fmt/lint/unit/fuzz/invariant, gas snapshot, Slither (any finding fails), strict halmos. `noir`: pinned-dep fetch + verify from an empty `~/nargo`, `compile.sh --check`, manifest-gated TXE (token, token_bridge, keystone), sole-consumer and stamp-constraint guards (each with its --self-test), `--exact` (nothing unpinned fetched), clean tree |
| `bridge-core.yml` | PRs touching `packages/bridge-core/**`, `contracts/evm/**`, the committed L2 artifacts, toolchain pins, the lockfile or this workflow | biome, typecheck, unit tests; the test script runs `forge build` first, so the ABI pins compare against fresh forge output and are never skipped |
| `local-network.yml` | PRs touching `packages/local-network/**`, toolchain pins, the lockfile or this workflow | biome, typecheck, unit tests (registry locking and reaping, owned process groups, run identity) |
| `demo.yml` | PRs touching `packages/demo/**`, `bridge-core`, the committed L2 artifacts, toolchain pins, the lockfile or this workflow | biome, typecheck, unit tests (the cast's derivations, the tour schema, the world-view decoder) |
| `deployer.yml` | PRs touching `packages/deployer/**`, the packages it imports (`bridge-core`, `demo`, `local-network`), the committed L2 artifacts, the keyed-run templates (`deployments/*.env.example`, which a unit test pins per role), toolchain pins, the lockfile or this workflow | biome, typecheck, unit tests. Live runs (`net:up` → `bridge deploy local` → `demo setup` → `smoke`) need the pinned Aztec node, so they run in the local phase gate |
| `integration.yml` | PRs touching `packages/integration/**`, the packages it drives (`bridge-core`, `demo`, `deployer`, `local-network`), toolchain pins, the lockfile or this workflow | biome, typecheck. The specs need the pinned Aztec node, so `bun run test:integration` runs in the local phase gate |
| `showcase.yml` → `_e2e.yml` | PRs touching `apps/showcase/**`, the packages it bundles or runs against (`bridge-core`, `demo`, `local-network`, `deployer`), the committed L2 artifacts or testnet manifest, toolchain pins, the lockfile or these workflows; `labeled` re-runs it | `showcase`: biome, typecheck, component tests, `build:testnet` with its manifest identity and bundle checks. `e2e`, only on the `e2e` label or a manual dispatch: the full browser suite (`bun run test:e2e`) against its own local network, state dir uploaded on failure; beside it, `presto`: the Presto suite (`bun run test:e2e:presto`), real proofs through a pinned presto-server behind an HTTPS proxy; presto-server alone gets the job's token, for the GitHub API calls that verify the bb it downloads. It first compares Presto's stdlib pin with the toolchain's (`e2e/run/presto-compat.ts`): equal runs the suite, exactly the pair named in its env (toolchain `6.0.0-rc.3`, Presto `6.0.0-rc.1`) warns and skips it, anything else fails. The proving harness (`test:proving`) is local only: it needs a cgroup v2 host for its 2-CPU quota |
| `fuzz-contracts.yml` | Nightly over `main` and `dev`, or by hand over one branch | An hour of Medusa over `contracts/evm/test/fizz` (`bun run test:evm:fuzz`) per branch, a matrix over the ref: a schedule fires from the default branch only, so the job checks out each branch itself. Fails on a broken property, a Medusa error, or fewer registered `property_*` checks than the suite declares. The corpus is cached per ref + suite + sources + config, a new ref starting from another's; a failed run uploads its logs and failing sequences. Not a PR gate. Medusa is the release binary, sha256-pinned in `setup-toolchains/medusa-<version>.sha256`; its crytic-compile comes from the Slither lock |
| `audit.yml` | PRs touching a `bun.lock` or `package.json` | `bun audit` over the workspace, `contracts/aztec/toolchain` and `packages/local-network/toolchain` lockfiles; advisory (not required), findings in the step summary |

Each caller ends in a `*-status` job, the one marked required: it fails when change detection fails, and when a relevant suite ended anything but `success`. The Sepolia fork suite needs an RPC, so it runs in the local phase gate rather than in CI.

## Branches

`main` is production: Workers Builds deploys it, and Galactica's team uses it. Fixes land on `dev` through squash-merged PRs, and `dev` reaches `main` through a `dev`→`main` PR merged with a merge commit (GitHub signs it), never a squash, so the two branches never diverge. A ruleset on each branch, with no bypass actors, admits changes only through a PR, refuses force-pushes and deletion, requires no approving review (the owner merges their own PRs) and no signatures, allows `squash` and `merge`, and requires the eight `*-status` contexts, each reported by GitHub Actions and non-strict (a PR need not be rebased on the branch tip first): `actionlint-status`, `bridge-core-status`, `contracts-status`, `demo-status`, `deployer-status`, `integration-status`, `local-network-status`, `showcase-status`. They can be required because each reports on every PR, a docs-only one included: the filter decides what runs, the status job always runs. Not required: `audit.yml` (it runs only on dependency PRs, advisory), the label-gated `e2e` job, and the Workers Builds check (a third-party app's).

Toolchain versions come from `toolchain.json` through `.github/actions/setup-toolchains`. CI never runs the aztec-up installer (unpinned remote scripts, an unlocked npm install): the aztec CLI, bb and the TXE server come from `contracts/aztec/toolchain`'s frozen lockfile, and nargo is the noir-lang release tarball, sha256-pinned in `setup-toolchains/nargo-<version>.sha256`. Bumping `noir` means bumping `@aztec-labs/aztec` in that lockfile and `nargo` (with a new pin file) together. halmos installs from `setup-toolchains/halmos-<version>.requirements.txt`, its whole dependency tree pinned by sha256 and wheels only, since the proof gate trusts halmos's own output; the file's header has the command that regenerates it. Slither installs the same way from `setup-toolchains/slither-<version>.requirements.txt`. It reads a `forge build src` of its own (`contracts/evm/scripts/slither.sh`): building the test mocks too hides findings in `src/`, and its own compile would `forge clean` the shared `out/`. `slither.config.json` excludes two detectors, `naming-convention` (the portal keeps upstream Aztec's `_param` names) and `pragma` (the npm dependencies declare their own ranges; `foundry.toml` pins the one solc), and filters no paths: Slither drops a result when any of its elements matches a filter, so one on `node_modules` would hide a `src/` finding that runs through a library. Each inline `slither-disable-next-line` carries its reason on the line above.

The local network's node (`aztecNode`) comes the same way: `packages/local-network/scripts/install-node.sh` installs `packages/local-network/toolchain`'s frozen lockfile (first migrated from aztec-up's npm install, whose resolution is unlocked) and the Foundry release that node ships with (`aztecNodeFoundry`, sha256-pinned in `toolchain/foundry-<version>.sha256`), then points `AZTEC_NODE_HOME` at them. A bump re-resolves that lockfile with Bun, which keeps every transitive pin that still satisfies, so its tree can lag a fresh aztec-up install's; a new `aztecNodeFoundry` needs a new pin file.

**Bumping Aztec.** Read the release's installer pins (`install.aztec-labs.com/<version>/versions`: nargo, the node's Foundry, node) and move `toolchain.json` with them. Every `@aztec-labs/*` pin takes the new version and every `@aztec-foundation/*` pin what `@aztec-labs/aztec.js` of that version pins (`npm view @aztec-labs/aztec.js@<version> dependencies`). A release days old fails the 7-day gate at resolution: add exact-name `minimumReleaseAgeExcludes` for its young closure to the root and both toolchain `bunfig.toml` files, run `bun install --ignore-scripts` in each, then remove them; a frozen install never consults the gate, so CI installs the committed locks with no exclude. A frozen install over that tree sees no change and never runs the node toolchain's one trusted build (`bcrypto`, which the node loads at start): reinstall it from an empty `node_modules` before a local network runs on it. Before anything from the new locks runs, check every new lock entry: its integrity against the registry, `npm audit signatures` over exactly those specs installed in an empty directory with each integrity equal to the lock's, and each provenance attestation's repository, tag and commit (`@aztec-labs/*` publish none, so for them it is the registry signature and an unchanged publisher). Then move the Nargo.toml tags, re-derive `contracts/aztec/scripts/noir-deps.sh`'s table from a clean-cache `nargo check` (its header has the recipe), and rebuild the artifacts with `compile.sh`.
