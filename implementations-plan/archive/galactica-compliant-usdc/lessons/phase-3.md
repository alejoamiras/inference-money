# Phase 3 — token wiring, integration, docs

Status: **green** (2026-10-01).

## Findings

1. **I2 was wrong: the proxy's and the bridge's class ids change** when their `token` dependency points at the fork (proxy `0x18d06d3b…af94` → `0x0d218cb0…d2e6`, bridge `0x2e9ade2e…96a3` → `0x2b818998…3d34`). Their bytecode and functions are identical. The only difference is `outputs.globals.storage`: Noir copies every contract crate's storage layout into the artifact of each crate that depends on it, so the fork's six new slots appear in both, and the artifact hash, which covers `outputs`, moves the class id. Nothing deployed depends on the old ids, since P9 redeploys all three, so the fix is to re-pin them in `artifacts.test.ts`. Until P9, `deployments/testnet.json` is the old deployment: its records no longer derive from the artifacts, so a testnet build from this branch fails at registration. `main` is unaffected.
2. **How an opener learns its request's commitment** (a design gap the plan left open). A sent tx returns no private return values (`send()` gives a hash or receipt plus offchain output), and the commitment embeds `random()` drawn while proving, so a simulation's return value is a different commitment. Options weighed:
   - reading the proving result's return values: possible only below the `Wallet` interface (`pxe.proveTx`), so no wallet-sdk wallet could do it;
   - reading the recipient PXE's pending partial notes: aztec-nr keeps them in crate-private capsules, with no API;
   - **an offchain effect `[REQUEST_OPENED_EFFECT, c]`**, emitted by the fork's own `_push_request_stamp` (upstream code untouched). `BaseWallet.sendTx` returns the proven run's effects (`provenTx.getOffchainEffects()`), the `Wallet` interface carries them, the embedded wallet's simulate-first pass doesn't change them, and an effect costs no constraints and reaches only the prover's own client. Chosen; the tag is pinned in Noir, the keystone and TypeScript, and checked distinct from the offchain-message identifier so wallets don't parse it as a message. The token's class id moved again (`0x0a1c52d7…87a5`).
3. **`payments.ts` records `sent` from a node wrapper.** A wallet proves and sends in one call, so the only point between proving and the node receiving the tx is the node object the wallet was built on. `PaymentGate.node` wraps it: a tx whose private logs carry the request's siloed completion tag (or whose public calldata carries the commitment) is recorded `sent`, with hash and expiry, before it is forwarded, and only if the reservation is still its owner's. Completion logs are tagged deterministically from (token, commitment), so `completionCount` sees a completion by anyone, and `payRequest` refuses a request already completed on chain. That narrows the two-device residual to payments in flight at the same time.
4. **A shared node install went stale under a removed worktree.** `~/.cache/inference-money/aztec-node-6.0.0-rc.1/node_modules` is a symlink into the worktree that ran `install-node.sh`, and that worktree is gone. Rather than repoint a shared cache, this worktree uses its own node home: the same pinned anvil and forge, plus a link to its own `packages/local-network/toolchain/node_modules`, selected with `AZTEC_NODE_HOME`.
5. **The plan's expiry numbers are in-circuit caps; the PXE rounds what it commits.** `computeTxExpirationTimestamp` caps the expiry at `anchor + MAX_TX_LIFETIME`, then rounds the span from the anchor down to whole hours, else half hours, else seconds, so exact caps don't reveal which functions ran. Measured: a 24 h merchant read and a tx that reads nothing both commit `anchor + 82800` (parity holds, the claim that matters); a 1 h entry commits `anchor + 1800`. The first A21 run asserted the raw `86399` and failed; the spec now derives the expected value with the same rounding, and plan mechanics 1 carries the correction.
6. **Arc 1 codex review, round 1** (GPT-6 Astra, high; session `01a0f4e6…`). Verdict: no merchant-proof or stamp-forgery bypass in the contract paths; every hint value leads to a proof or a refusal. Four `payments.ts` findings, all accepted and fixed:
   - *Reservation takeover inside one gate* (high, reproduced by codex): after a reservation lapsed, a second attempt overwrote the gate's expectation for the request, the first attempt's tx was recorded under the second's owner, and both sent. Now one attempt per request per gate (a second is refused), cleanup is owner-conditional, and a unit test replays the scenario.
   - *An unfinalized revert released the request* (high): a pruned block could resurrect the reverted tx next to a retry. Records now move only on finalized evidence: `paid` or released at a finalized receipt, and expiry measured against the finalized block.
   - *A wallet outside the gate's node* (high): an ambiguous send through an unwrapped node left a releasable reservation. `payRequest` now refuses any wallet not built by `PaymentGate.bindWallet`, and a send the gate missed is recorded as sent and reported, never released.
   - *Loose public matching* (medium): any calldata holding the commitment counted as a payment. The gate now matches the token's `transfer_public_to_commitment` with the commitment as its second argument, and the integration suite pays publicly through `payments.ts`.
7. **Rounds 2 and 3 (same session).** Round 2 confirmed the four fixes and found one more high path, reproduced: a stalled send response of attempt A, whose tx then finalized reverted, arrived after B had replaced it, and `confirmSent` overwrote B's record with A's, which the next settle released while B was in flight. Fixed: the gate remembers the attempts it recorded, those never touch the store after `send()` returns, and a missed send writes only over its own reservation; the two-gate scenario is a unit test. Round 3: converged, no remaining finding (confidence high for the fix, moderate overall, assuming exclusive store locking and bound wallets). The loop closed at its 3-round cap.
8. **Local deploy and `verify` pass on the fork** (`RUN_ID=p3c`), including the new merchant-role checks (admin == deployer, no handover pending, the guardian slot's delay 86400 with nothing pending) and every slot read from the artifacts' layouts.
